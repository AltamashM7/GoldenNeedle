# Decision log

These decisions describe the current product and architecture direction. A later Orchestrator instruction may explicitly change an **OPEN / MAY CHANGE** item.

Current status authority: `Docs/current-state.md`.

Detailed pre-Phase-5A foundation architecture: `Docs/pre-phase5a-foundations.md`.

| Decision | Status | Rationale |
|---|---|---|
| Unity 6.5 | **LOCKED** | Establishes the engine baseline for SIH 2026 development and avoids version drift. |
| URP | **LOCKED** | Provides the current Unity rendering baseline while supporting a deliberately simple, CPU-conscious presentation target. |
| CPU-first / no required dedicated GPU | **LOCKED** | The application must run acceptably on an ordinary computer without requiring a discrete GPU. |
| Camera experience integrated into Unity | **LOCKED** | The user-facing product must provide one cohesive application rather than require an external tracking program. |
| Pose provider remains replaceable | **LOCKED ARCHITECTURAL DIRECTION** | The provider boundary protects the rest of the project from backend changes. Stock MediaPipe/TFLite and OpenVINO CPU FP32 are both available behind the current provider integration. |
| Full-body digital embodiment, not merely gesture-triggered buttons | **LOCKED PRODUCT DIRECTION** | Continuous body-driven avatar control is the core innovation and fitness interaction model. |
| Engine-owned canonical skeleton | **LOCKED ARCHITECTURAL DIRECTION** | Downstream systems need a stable project-owned body representation independent of provider-specific results. |
| Pose and locomotion are separate systems | **LOCKED ARCHITECTURAL DIRECTION** | Body reproduction and conversion of actions such as jogging in place into world movement have different semantics and tuning needs. |
| Modular Hub/course structure | **LOCKED ARCHITECTURAL DIRECTION** | Independent environments and courses reduce coupling and support parallel content ownership. |
| Git LFS enabled from initial repository setup | **CURRENT REPOSITORY DECISION** | The local Git LFS client and repository filters/endpoint are present; current `.gitattributes` has no LFS-managed patterns, so this state is preserved and reported rather than expanded speculatively. |
| GitHub Desktop for user's normal Git operations | **CURRENT WORKFLOW DECISION** | The USER uses GitHub Desktop for normal branch, commit, push, and PR-related mutations. |
| Web Orchestrator + Web Builder / Luna as scoped builders | **CURRENT DEVELOPMENT WORKFLOW** | Architecture/integration review is kept separate from implementation. Complex fixes belong to the intelligent Web Builder; Luna is for tightly scoped routine work. |
| Official Unity Codex plugin `unity@unity-agent-plugin` | **CURRENT DEVELOPMENT TOOLING DECISION** | Provides Unity-specific Codex skills through the first-party Unity Technologies integration; it remains outside the Golden Needle runtime. |
| Official Unity CLI + Pipeline package `com.unity.pipeline` `0.5.0-exp.1` + Unity MCP | **CURRENT DEVELOPMENT TOOLING DECISION** | Gives Codex a supported path to inspect and perform harmless operations in the live Unity Editor while keeping the integration out of shipped product dependencies. |
| Integrated laptop webcam is a supported baseline input | **LOCKED SPIKE REQUIREMENT** | The technical baseline must work with an ordinary built-in webcam; external or depth hardware is optional. |
| Partial-body tracking is valid | **LOCKED SPIKE REQUIREMENT** | Upper-body control data remains usable when legs are outside the frame; trust is evaluated per landmark and missing lower-body landmarks do not reject the whole pose. |
| MediaPipeUnityPlugin `0.16.3` + MediaPipe `0.10.22` semantics remain the compatibility baseline | **LOCKED CURRENT COMPATIBILITY RULE** | Current preprocessing, ROI/tracking, landmark decoding, world-landmark semantics and canonical behavior are the known-good reference and are reused even when neural inference is accelerated. |
| Stock MediaPipe/TFLite CPU backend remains available | **LOCKED FALLBACK RULE** | The known-safe TFLite path must not be deleted or weakened merely because OpenVINO is faster on the current proof machine. |
| OpenVINO CPU FP32 backend | **USER-VALIDATED BEST-TESTED LOW-END BACKEND** | Additive OpenVINO 2026.3.0 integration reuses MediaPipe graph semantics and materially improves live compute performance on the i3-7100U / HD620 test machine. It does not silently replace the fallback or serialized/default policy. |
| OpenVINO exact detector/landmark models | **LOCKED INTEGRATION RULE** | The runtime uses the exact models extracted from the production task bundle; no detector densification/conversion or alternate weights are allowed without a separate equivalence decision. |
| OpenVINO persistent worker + two-slot latest-frame mailbox | **USER ACCEPTED — PASS** | One active inference plus one replaceable newest pending frame removes avoidable Update-bound launch delay while preserving no-backlog/latest-frame semantics. No FIFO/history/replay/catch-up queue is allowed. |
| WebCamCPU/GetPixels32 acquisition for OpenVINO | **USER ACCEPTED — PASS FOR CURRENT MILESTONE** | Reused CPU camera pixels + reusable 320x240 preparation removes the dominant AsyncGPUReadback latency on the USER machine and enables roughly 27–29 fresh poses/s with a ~30 FPS camera. |
| ExistingReadback acquisition remains available | **LOCKED FALLBACK / REFERENCE RULE** | The older readback path remains selectable for fallback, comparison, and hardware-specific compatibility. |
| Body inference target 320x240 | **CURRENT BEST-TESTED BASELINE** | It preserves tracking quality while reducing upstream preparation cost; lowering the image further does not shrink the fixed 224/256 neural tensor sizes. |
| Bounded latest-frame camera/inference scheduling | **LOCKED RUNTIME RULE** | At most one active inference and one replaceable newest prepared/pending frame are allowed. Latest useful frame wins; no historical frame queue or inference backlog is permitted. |
| Motion Engine long-lived phase branch | **CURRENT WORKFLOW DECISION** | `engine/pose-tracking-spike` carries core Motion Engine work until the USER explicitly approves a later merge strategy; checkpoints are not mechanically merged to `main`. |
| Phase 2 canonical joint set and partial validity | **CURRENT PHASE 2 IMPLEMENTATION / PRESERVE AS V1** | Engine-owned frame contains the 20 named canonical joints plus trusted midpoint derivations; missing joints do not invalidate the whole frame. Richer motion work must be additive rather than destructively changing this accepted compatibility contract. |
| Phase 2 canonical coordinates | **CURRENT PHASE 2 IMPLEMENTATION** | Image x increases right and y increases up. Canonical 3D uses +X camera/view right, +Y up, +Z away. Conversion occurs once at the provider-to-canonical boundary. |
| Single canonical camera / inference frame | **PHASE 4 USER ACCEPTED** | Front-facing status does not request horizontal inference mirroring; vertical/rotation transport remains. Display mirror is presentation-only and canonical normalized/world mapping is unchanged. |
| Phase 4 signed canonical-to-avatar mapping | **PHASE 4 USER ACCEPTED** | Corrected frontal source semantics are `R≈-X, U≈+Y, F≈-Z`; the accepted signed reference mapping drives procedural and Animator Humanoid paths. |
| Phase 4 positional limb retargeting + analytic IK | **PHASE 4 USER ACCEPTED / FALLBACK REFERENCE** | Normalized limb targets map through the accepted reference basis and preserve avatar-authored proportions; project-owned analytic two-bone IK remains authoritative while richer orientation is introduced additively. |
| Phase 4 modular measurement calibration | **PHASE 4 USER ACCEPTED** | Comfortable body reference establishes torso axes/proportions and each limb chain accumulates independent measurements; missing limbs do not globally block motion. |
| Stable Phase 3 canonical filter remains calibration/locomotion authority | **LOCKED CURRENT BOUNDARY** | Calibration and Phase 5A continue to consume the accepted `1.0 / 0.05 / 1.0` stabilized frame even while avatar-only responsiveness is tuned independently. |
| Avatar-drive pose source is independently selectable | **IMPLEMENTED / PRESERVE FOR TUNING** | Avatar solving can use Stable, Raw, or responsive One Euro variants without changing calibration or locomotion. The selected frame is shared consistently by rotation solving, kinematic targets and torso/source mapping. |
| Avatar-drive serialized enum meanings | **LOCKED COMPATIBILITY RULE** | `Stable=0`, `Raw=1`, `A=2`, `B=3`, `C=4`, `D=5` are preserved so existing scene/settings serialization does not silently change meaning. |
| Avatar responsive profiles A/B/C/D | **IMPLEMENTED / FINAL WINNER DEFERRED** | A/B proved the latency-stability tradeoff; C/D isolate beta with `minCutoff=1.0`. The USER intentionally deferred final fine-tuning and default selection. |
| Raw avatar-drive mode | **PRESERVED LATENCY REFERENCE** | USER reports Raw feels effectively instant but slightly less stable. It remains a valuable upper-bound responsiveness reference rather than being forced as the production default. |
| Humanoid render-rate presentation smoothing | **IMPLEMENTED / SEPARATE TUNING LAYER** | Exact Phase 4 solve remains authoritative. Presentation smoothing affects visible rotations only and does not alter canonical tracking, calibration, IK targets or locomotion. |
| Motion-engine latency/performance optimization milestone | **CURRENT MILESTONE COMPLETE; FURTHER TUNING DEFERRED** | Major bottlenecks were removed and the best tested path approaches camera cadence. Additional smoothing/performance tuning is optional future work, not a blocker to normal development. |
| Phase 5A hybrid locomotion | **IMPLEMENTED / NOT USER ACCEPTED** | Finite support-foot camera-space displacement and cadence extension are fused while Phase 4 pose reproduction stays separate. Acceptance work resumes only after the approved pre-Phase-5A foundations are handled. |
| Phase 5A root estimation | **IMPLEMENTED / NOT USER ACCEPTED** | Physical translation authority is the ankle/heel/toe support-base model. Torso apparent scale is auxiliary depth corroboration only. |
| Phase 5A cadence fusion | **IMPLEMENTED / NOT USER ACCEPTED** | Cadence extends range only when rhythmic lower-body stepping exists and meaningful physical root velocity is small; physical motion suppresses cadence to avoid obvious double-counting. |
| Phase 5A recenter | **IMPLEMENTED / NOT USER ACCEPTED** | Public `Recenter()` makes the current physical location the new tracking origin while preserving current virtual X/Z. |
| Phase 5A vertical/root authority | **LOCKED PROTOTYPE RULE** | Locomotion writes avatar-root X/Z only; root Y and rotation remain excluded. |
| Phase 5A physical coordinate mapping | **IMPLEMENTED / NOT USER ACCEPTED** | Camera-space physical displacement is scaled then mapped through the accepted Phase 4 reference canonical-to-avatar axis map before world X/Z application. Live body heading affects cadence only. |
| Phase 5A physical scale defaults | **FIRST-QA TUNING DECISION** | Current lateral/depth defaults are `0.9 / 1.5`; they remain Inspector-tunable rather than production-locked. |
| Phase 5A support model v3 | **IMPLEMENTED / NOT USER ACCEPTED** | Common `(L+R)/2` support displacement drives room movement while differential `(L-R)/2` gait evidence attenuates depth trust. |
| Phase 5A known lean-translation issue | **OPEN / MUST RESOLVE BEFORE ACCEPTANCE** | USER QA found that planted-feet leaning can still produce unwanted translation. |
| Phase 5A stationary cadence robustness | **OPEN / MUST RESOLVE BEFORE ACCEPTANCE** | USER QA found cadence stepping while stationary is not yet robust enough. |
| Phase 5A F12 Lab/Game mode | **IMPLEMENTED / NOT USER ACCEPTED** | F12 is presentation-only. Lab keeps webcam/debug IMGUI; Game hides IMGUI and uses the persistent third-person camera. Foundation B preset selection remains orthogonal to this mode toggle. |
| Tracking vs presentation data | **LOCKED BOUNDARY** | Phase 5A consumes genuine stabilized tracking data; smoothed avatar rotations are presentation-only. |
| External/phone camera selection | **IMPLEMENTED** | Persist WebCamDevice name; Inspector enumerates devices and `V` cycles ordinary devices. Phones require OS/UVC/virtual-webcam exposure; no phone-specific network protocol exists. |
| Manual camera rotation | **IMPLEMENTED** | Auto follows `videoRotationAngle`; optional 0/90/180/270 overrides drive inference preparation and Lab display/convention state. Front-facing metadata still does not imply horizontal inference mirror. |
| Camera hot-switch safety | **IMPLEMENTED** | Pending switch blocks new old-camera work, waits for active work, restarts one provider pipeline, bumps source/session convention version, and invalidates calibration/Phase 5A origin assumptions. |
| Pose target cadence 30 FPS | **CURRENT PROTOTYPE TARGET** | 30 FPS is a maximum/request target, not a result-rate promise. With OpenVINO + WebCamCPU, full-body USER evidence reaches roughly 27–29 fresh results/s on the current proof machine. |
| Pipeline timing diagnostics | **IMPLEMENTED / RETAIN** | F7 exposes capture/render/request/result data, acquisition and inference timing, pose age, launch-origin/scheduling evidence and fallback information without per-frame log spam. |
| Lab clear-only camera | **IMPLEMENTED / RETAIN** | In Lab, the persistent Camera remains enabled with culling mask zero and solid-color clear so Unity does not show `No cameras rendering`, while IMGUI retains fitted whole-frame webcam geometry. F12 restores the original world render settings. |
| Sentis GPUCompute on Intel HD 620 | **REJECTED FOR CURRENT LOW-END BACKEND** | Same-run evidence showed Sentis GPUCompute slower than CPU and D3D12 emitted fence warnings. This does not prohibit stronger GPUs from being evaluated later. |
| Custom native Windows camera capture | **DEFERRED** | WebCamCPU/GetPixels32 already removed the dominant readback bottleneck without adding a platform-specific camera stack. |
| Pre-Phase-5A foundation track | **IN PROGRESS — A/B IMPLEMENTED; USER MANUAL QA DEFERRED; C–E NOT STARTED** | Complete unified commands/speech, camera presets, rich canonical orientation, MediaPipe hand landmarks, and optional-bone retargeting before returning to Phase 5A acceptance. Detailed authority: `Docs/pre-phase5a-foundations.md`. |
| Unified command/action layer | **IMPLEMENTED / ORCHESTRATOR CODE-AUDITED / USER MANUAL QA DEFERRED** | Keyboard, speech, UI and future inputs invoke shared runtime actions rather than duplicating behavior or simulating key presses. |
| Speech commands | **IMPLEMENTED / ORCHESTRATOR CODE-AUDITED / USER MANUAL QA DEFERRED** | Speech remains a replaceable input backend with Inspector-editable phrase→action mappings, cooldown, optional wake prefix, confidence thresholds and graceful unsupported-backend behavior. Real microphone QA is deferred. |
| Foundation A verification workflow | **READ-ONLY / LOCKED HYGIENE RULE** | The permanent Foundation A workflow uses `contents: read`, performs smoke/static regression checks only, and must never auto-apply migrations, commit, or push repository changes. |
| Camera view presets | **IMPLEMENTED / USER MANUAL QA DEFERRED** | One primary `ThirdPersonLabCamera` owns data-driven Back/Front/Left/Right/FullBody/Hands/LeftHand/RightHand presets, retained-heading placement, smooth transitions and safe semantic focus fallbacks. Speech invokes selection through the shared command layer; preset selection never toggles Lab/Game. Independent Orchestrator diff audit and later USER visual/runtime QA remain required. |
| Camera preset compatibility baseline | **LOCKED FOUNDATION B RULE** | `Back` is seeded from the previous third-person values (distance 4.0, height 2.2, look height 1.15, response 7.0, FOV 55) so Foundation B does not silently replace the established F12 Game View behavior. |
| Camera preset focus fallbacks | **LOCKED FOUNDATION B RULE** | Hands prefers the midpoint of two valid hands, then one available hand, then body/root. Left/Right hand prefer their chain tip, then lower arm, then body/root. Missing optional targets never invalidate tracking or rig binding. |
| Rich canonical motion representation | **LOCKED PRE-5A ARCHITECTURAL DIRECTION** | Introduce a versioned/additive provider-independent motion representation for position + bone orientation + confidence + optional articulation while preserving CanonicalBodyV1. |
| Canonical orientation authority | **LOCKED PRE-5A ARCHITECTURAL DIRECTION** | Use validated orthonormal anatomical bases with handedness, confidence and twist observability as canonical orientation truth. Quaternions are produced only at the final avatar-rotation/application stage. |
| General bone-orientation reconstruction | **LOCKED PRE-5A ARCHITECTURAL DIRECTION** | Solve primary direction plus independent secondary anatomical evidence for all supported bones. Do not fix forearm twist with a special-case patch while other bones remain position-only. |
| Swing/twist uncertainty handling | **LOCKED PRE-5A ARCHITECTURAL DIRECTION** | Update twist only when secondary evidence is trustworthy; preserve recent trusted twist through short ambiguity and use controlled fallback after longer loss instead of inventing rotation. |
| MediaPipe hand landmarks | **APPROVED PRE-5A FEATURE / PROVIDER CHOICE TO AUDIT** | Use MediaPipe-provided hand landmarks for useful palm/finger articulation. Perfect finger mocap is not required. Audit separate Hand Landmarker vs Holistic; preserve the optimized body path unless evidence justifies a combined provider. |
| Body tracking remains priority stream | **LOCKED PERFORMANCE RULE** | Hand inference may run independently/adaptively/lower cadence and must not casually destroy the near-camera-cadence body path or introduce unbounded queues. |
| Optional-bone/capability retargeting | **LOCKED PRE-5A ARCHITECTURAL DIRECTION** | Bind and drive only bones the avatar actually has. Missing finger/hand/detail bones must never crash or invalidate unrelated body retargeting. |
| Foundation implementation order | **CURRENT EXECUTION PLAN** | A: command/speech → B: camera presets → C: rich orientation → D: hand landmarks → E: optional orientation/finger retarget → comprehensive A–E USER manual/runtime QA → return to Phase 5A. |
| Foundation QA sequencing | **USER DECISION — MANUAL QA DEFERRED, NOT WAIVED** | Foundations A–E may continue sequentially with focused implementation/code/automated verification. USER manual/runtime acceptance is deferred to one comprehensive pass after all five are built; no foundation is auto-accepted and speech/camera visual QA remains pending until then. |
| Phase 6 | **NOT STARTED** | Do not begin Phase 6 until the USER explicitly advances the project beyond the current prerequisite/Phase 5A state. |
